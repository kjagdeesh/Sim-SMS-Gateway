Network safety

The phone API uses plain HTTP on port 8765. Use it only on a trusted network; never expose or port-forward it to the public internet.

How it works

Your app or browser sends a JSON request directly to the Android phone. The gateway validates it, submits the SMS through the phone's default SIM, and stores the result in the app's private SQLite database.

Getting started

Prepare the Android phone, launch the local API, and connect the browser playground.

Requirements

  • An Android phone with a SIM that can send SMS.
  • SMS permission granted to Sim SMS Gateway when prompted.
  • .NET 10 SDK and the Android workload to build from source.
  • Node.js 18+ to run the browser playground.
  • The phone and browser device must be able to reach one another on a trusted network.

Build and install

From the repository root in PowerShell, build and install the Android app:

PowerShell
dotnet build .\build\sim-sms-gateway\SimSmsGateway.sln
dotnet build .\build\sim-sms-gateway\SimSmsGateway\SimSmsGateway.csproj -t:Install -f net10.0-android

Start the gateway

  1. 1
    Open Sim SMS Gateway and select Dashboard → Server.
  2. 2
    Tap Start server and allow SMS permission if Android asks.
  3. 3
    Copy a Same Wi-Fi address and the API key. Use the Wi-Fi address from another device; localhost refers to the current device.
  4. 4
    Keep the app open while using the API. The server is not a background service.

Run and connect the browser playground

From build\sim-sms-gateway\web, run npm start, then open http://localhost:8766. Choose Connect, enter the phone's address and API key, and confirm the status changes to Connected.

The connection check calls the unauthenticated health endpoint and then an authenticated stats endpoint. The browser connects directly to the phone; the Node process only serves static website files.

Documentation site URL

When using the included Node server, this standalone site is available at http://localhost:8766/docs/.

Connect and preferences

The Connect dialog validates the URL, checks /health, and requests /api/v1/stats with the API key. The server URL is stored in browser local storage; the API key is stored in session storage for the current tab. Select Disconnect in the top bar to clear both saved connection values; this does not stop the Android server. Country and theme preferences use local storage.

The included static server defaults to 127.0.0.1:8766. This address is loopback-only; for an externally hosted website, the user's browser still needs a network route to the phone. HTTPS-hosted pages may be blocked from calling the phone's plain-HTTP API by browser mixed-content rules.

Live API tester

The API documentation page can send live requests to the connected phone. Health/history/stats requests do not send SMS. Single and bulk send requests show a confirmation prompt before sending.

Protect the browser session

Do not leave the API key in session storage on a shared computer. Clear browser storage when finished.

Sending messages

Send one SMS or the same text to a validated list of recipients through the phone's SIM.

Single message

  1. 1
    Open Send Messages and select Single message.
  2. 2
    Select a default country. Its calling code is shown beside the number field. Local numbers use this code; numbers starting with + or 00 are treated as international.
  3. 3
    Enter a valid phone number and message (up to 1,600 characters), then review the international-format preview.
  4. 4
    Press Send SMS. The result panel shows the HTTP response and accepted/failed status.

API destinations must match E.164 format: ^\+[1-9]\d{7,14}$. For example, +14155550123.

Bulk message

  1. Select Bulk messages.
  2. Type or paste numbers separated by new lines, commas, semicolons, or spaces; press Enter to add typed entries.
  3. Or import a .csv or .txt file up to 512 KiB. The importer looks for a phone-number-like value in each row.
  4. Fix or remove red invalid entries. Duplicate normalized numbers are skipped.
  5. Send to 1-100 unique E.164 recipients with one shared message.

The server validates all recipients before sending anything. If validation passes, it sends sequentially; one Android/SIM send failure does not stop the remaining recipients.

When the form clears

  • After a successful single send, the destination and message are cleared.
  • After a bulk send, the message and recipients clear only if every recipient succeeded.
  • Failed sends and partially failed bulk batches preserve the form so the user does not lose inputs. The selected default country is retained.

Success means Android accepted the submission. It is not a carrier delivery receipt. Sending may incur charges; only message recipients who have agreed to receive SMS.

History and statuses

Each handled SMS attempt is saved on the Android device and shared by the app dashboard and API.

Status meanings

success

Android accepted the SMS request for submission. Delivery to the recipient is not confirmed.

failed

Android or the SIM rejected the submission; the record may contain an error reason.

Find records

  • The web Dashboard shows total, successful, failed, and success-rate statistics. It pages through 25 entries at a time.
  • The Android Message History page filters All, Success, or Failed and loads 50 entries at a time.
  • Both views show newest entries first. The web page can refresh stats and history.
  • The API supports status filtering and limit/offset paging. See API reference.

What is saved

The phone stores the destination, message text, status, error (if any), timestamp, and optional bulk batch ID. Requests rejected by validation before the sender is called are not send attempts and are not written to history.

The database is in the app's private data directory. No automatic history pruning is implemented; uninstalling the app removes its private app data.

Bulk results

A validated bulk request can return HTTP 200 while some individual recipients have failed status. Check each result, not only the HTTP status.

API

REST API reference

The Android app exposes a small JSON API on port 8765. Replace PHONE_IP with the address shown on the phone's Server page.

HTTP is not encrypted

Use the API only on a trusted network. The bearer key and message contents travel in cleartext over HTTP.

Authentication

All API endpoints except GET /health require the bearer key generated by the Android app. The key changes when the app restarts. Include this header:

HTTP header
Authorization: Bearer YOUR_API_KEY

POST requests require Content-Type: application/json. The API accepts E.164 destinations and messages up to 1,600 characters.

Endpoints

Method and pathAuthRequestSuccess
GET /healthNoNone200: {"status":"online"}
POST /api/v1/messagesBearerto E.164; message string202: accepted, record ID
POST /api/v1/messages/bulkBearerrecipients array (1-100 unique E.164); message200: batch ID, counts, per-recipient results
GET /api/v1/messagesBearerstatus optional; limit 1-200 (default 50); offset 0+ (default 0)200: items, limit, offset
GET /api/v1/statsBearerNone200: total, success, failed

Responses and errors

StatusMeaning

API

Code examples

These examples send one SMS. Replace the phone address and API key with values from the Server page. Sending an SMS may incur charges.

Use an authorized recipient

Test with your own number or a recipient who has agreed to receive the message.

cURL - POST /api/v1/messages
curl -X POST "http://PHONE_IP:8765/api/v1/messages" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"to":"+14155550123","message":"Hello from my app"}'
JavaScript - Fetch
const baseUrl = "http://PHONE_IP:8765";
const apiKey = "YOUR_API_KEY";
const response = await fetch(`${baseUrl}/api/v1/messages`, {
  method: "POST",
  headers: {
    Authorization: `Bearer ${apiKey}`,
    "Content-Type": "application/json"
  },
  body: JSON.stringify({ to: "+14155550123", message: "Hello from my app" })
});
console.log(response.status, await response.json());
Python - requests
import requests

base_url = "http://PHONE_IP:8765"
api_key = "YOUR_API_KEY"
response = requests.post(
    f"{base_url}/api/v1/messages",
    headers={"Authorization": f"Bearer {api_key}"},
    json={"to": "+14155550123", "message": "Hello from my app"},
    timeout=60,
)
print(response.status_code, response.json())

JSON request

application/json
{
  "to": "+14155550123",
  "message": "Hello from my app"
}

Bulk request

POST /api/v1/messages/bulk
{
  "recipients": [
    "+14155550123",
    "+919876543210"
  ],
  "message": "Hello everyone"
}

History and stats examples

Use GET /api/v1/messages?status=failed&limit=25&offset=0 to page through failed attempts. Use GET /api/v1/stats for aggregate counts. Both require the bearer key.

System architecture

A small platform-neutral API core is hosted by the MAUI Android app, which supplies the SMS sender and a shared on-device store.

Browser / API client
       | HTTP + JSON over trusted LAN :8765
       v
GatewayHost (Android app lifecycle, key, addresses)
       |
       v
SmsApiServer (TCP listener, HTTP parser, routes, auth, CORS)
       |                         |
       v                         v
SmsRequestValidator       SmsMessageStore
       |                  SQLite: messages.db
       v
ISmsSender
       |
       v
AndroidSmsSender -> Android SmsManager -> default SIM -> carrier

Responsibilities

  • GatewayHost: owns the API key, listener lifecycle, port, and local address discovery.
  • SmsApiServer: parses HTTP, authenticates, validates/routs requests, calls the sender, and writes JSON responses.
  • SmsRequestValidator: enforces E.164 numbers, message length, and bulk recipient limits.
  • ISmsSender: separates the API core from platform SMS dispatch.
  • AndroidSmsSender: submits single or multipart text through Android's default SMS manager.
  • SmsMessageStore: persists each handled attempt and serves history and stats.

Lifecycle

  1. App startup opens messages.db in its private data directory and creates a random 32-byte API key.
  2. The user starts the gateway; the host binds a TCP listener to all network interfaces on port 8765.
  3. The client sends an authenticated request; the server validates it and invokes the Android sender.
  4. The store records accepted sends and handled send failures. The same store instance is used by mobile pages.
  5. Stopping the server cancels its accept loop. Closing the app stops the in-process server.

The browser site's Node server is a separate, static-file-only process. Browser JavaScript connects directly to the phone; no SMS request passes through Node.

HTTP server internals

The API is a hand-built HTTP server over .NET's TcpListener, not ASP.NET Core or Kestrel.

Request processing

  1. Accept one TCP client, then parse its request line, headers, and body.
  2. Handle CORS OPTIONS requests and the unauthenticated GET /health route.
  3. For API routes, validate the bearer key, content type, JSON, and route-specific input.
  4. Call the sender or read from SQLite, serialize the response, and close the connection.

Limits and behavior

PropertyImplementation
Bind address / portIPAddress.Any:8765; available on phone network interfaces.
ConcurrencyOne accepted client is handled at a time; listen backlog is 16.
Request timeout60 seconds per client request.
Header/body limits16 KiB headers; 32 KiB body.
Body framingReads according to Content-Length; chunked request bodies are not implemented.
ConnectionOne request per connection; response includes Connection: close.
CORSAllows any origin, GET/POST/OPTIONS, and Authorization/Content-Type headers.
TransportPlain HTTP; TLS and rate limiting are not implemented.

Authentication and route details

The API key is 32 cryptographically random bytes encoded as URL-safe Base64. It is held in memory, shown on the Server page, and regenerated at process start. The server compares equal-length key bytes using a fixed-time comparison. CORS preflight OPTIONS is handled without authentication.

Bulk requests are fully validated before dispatch. Valid recipients are submitted sequentially, and the response contains an individual result for each number. A single handled sender failure returns HTTP 503; a processed bulk request returns HTTP 200 even if one or more result statuses are failed.

Do not expose this listener

CORS is not authentication or encryption. Plain HTTP can expose the key, destinations, and message bodies to anyone able to observe the network.

SQLite and storage

Message history lives on the phone in the app's private data directory. The API and mobile pages read the same database.

Database path: FileSystem.AppDataDirectory/messages.db.

messages table

ColumnMeaning
idAuto-incrementing record ID.
batch_idNullable ID shared by records in a bulk batch; null for single messages.
destinationValidated E.164 destination.
messageMessage text.
statusConstrained to success or failed.
errorNullable failure reason.
created_atISO 8601 UTC timestamp.

Writes and reads

  • Each handled send attempt is inserted after Android accepts it or reports a handled send failure.
  • Invalid input rejected before sending is not stored.
  • Indexes support status and newest-first lookups; a lock serializes access to the shared SQLite connection.
  • Stats are calculated from stored rows; history supports status filtering, limit, and offset.
  • There is no automatic retention/pruning job. Uninstalling the app removes its private data.

Neither the website nor its Node static server maintains another message database.

Troubleshooting

Use the request status and gateway state to narrow down connection, validation, and SMS issues.

Symptom / statusChecks
Browser cannot connectStart the server; use the phone's Same Wi-Fi address, not another device's localhost; check Wi-Fi, firewall, and client isolation.
HTTP 400Check JSON syntax, E.164 formatting, nonblank message, 1,600-character limit, unique bulk numbers, and history query ranges.
HTTP 401Copy the key currently displayed by the app and send it as a Bearer token. The key changes after restart.
HTTP 404Check the method and exact endpoint path.
HTTP 413 / 431Reduce the request body below 32 KiB or request headers below 16 KiB.
HTTP 415Set Content-Type: application/json on POST requests.
HTTP 503 (single)Check SMS permission, default SIM, signal, SIM capability, and carrier account status.
Bulk HTTP 200 with failuresCheck each result's status and error. The batch continues after an individual send failure.
HTTPS page cannot call phone APIBrowsers may block HTTPS-to-HTTP requests as mixed content. The phone API has no TLS endpoint.

Check service state

  1. Confirm the Android Server page says Running.
  2. From a reachable client, request GET http://PHONE_IP:8765/health.
  3. Reconnect with the current API key if the app was restarted.
  4. Use Message History or GET /api/v1/messages to inspect recorded send errors.

OPERATIONS

Security and privacy

The gateway is intended for trusted local networks. It is not a hardened public SMS service.

Network and API key

  • The phone listens on all network interfaces at port 8765 using plain HTTP. There is no TLS encryption.
  • The bearer key authenticates API routes but cannot protect data from network interception without TLS.
  • CORS allows any origin to support browser clients; it is not an access-control boundary.
  • Do not port-forward the phone, expose the port publicly, or use an untrusted Wi-Fi network.
  • Do not put the key in public source code or share browser sessions. The browser keeps it in session storage for the current tab.

Message data

  • Destinations, message text, status, timestamp, and error details are stored in the app's private SQLite database.
  • The browser dashboard reads history from the phone; it does not persist a second copy of the message database.
  • The About/Developer pages may request public profile/project data from GitHub. SMS bodies and phone numbers are not sent to GitHub by the app.
  • Uninstalling the Android app removes its private database. The current app does not automatically prune history.

Responsible sending

Only send to recipients who have agreed to receive messages. Messages use the phone's default SIM and carrier plan; charges and carrier restrictions may apply.

Build and test

PowerShell - build and offline tests
dotnet build .\build\sim-sms-gateway\SimSmsGateway.sln
dotnet run --project .\build\sim-sms-gateway\SimSmsGateway.Tests\SimSmsGateway.Tests.csproj

The offline API tests use a fake sender and never send a real SMS. To exercise Android dispatch, install the app on an authorized device with an SMS-capable SIM and grant permission.

Extending the sender

Implement ISmsSender for a new platform or fake, then supply it when constructing SmsApiServer. Keep request validation and persistence in the core so API behavior remains consistent across sender implementations.
